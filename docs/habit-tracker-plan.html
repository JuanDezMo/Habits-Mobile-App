Identificadores para pruebas E2E

Cada elemento interactivo y cada estado que una prueba deba verificar lleva un testTag. El mismo identificador funciona en Maestro y en Appium, en Android y en iOS.

PlataformaCómo lo ven Maestro y AppiumConfiguración
Androidresource-idtestTagsAsResourceId = true una vez en la raíz, en todas las versiones
iOSaccessibilityIdentifierNinguna. Compose Multiplatform lo traduce solo.
Convención · pantalla_elemento[_id] 
object TestTags {
  const val PIN_DOTS = "pin_dots"
  const val PIN_ERROR = "pin_error_text"
  fun pinKey(n: Int) = "pin_key_$n"
  fun todayCheck(id: Long) = "today_check_$id"
  fun todayStreak(id: Long) = "today_streak_$id"
  const val FORM_TITLE = "form_title_input"
  const val DETAIL_STREAK = "detail_stat_streak"
  fun calDay(d: LocalDate) = "detail_cal_day_$d"
}
Ejemplo · flujo Maestro 
# .maestro/04_checkin.yaml
appId: co.com.buildinghabittracker
---
- launchApp
- tapOn: { id: "pin_key_1" }
- tapOn: { id: "pin_key_3" }
- tapOn: { id: "pin_key_5" }
- tapOn: { id: "pin_key_7" }
- tapOn: { id: "today_check_1" }
- assertVisible:
    id: "today_streak_1"
    text: "🔥 6"
Reglas
  • Llevan identificador los elementos interactivos (botones, campos, casillas, pestañas) y los estados clave (errores, racha, cumplimiento, bloqueo, mensajes).
  • En las listas, el identificador usa el id del hábito, nunca su posición ni su título.
  • Un identificador nunca contiene datos del usuario: nombre, email ni título del hábito.
  • No se usan textos visibles ni contentDescription como selector, porque cambian con el idioma y son para lectores de pantalla.
  • Los diálogos de permisos son del sistema. Se resuelven con permissions en Maestro y autoGrantPermissions en Appium.
  • Maestro se ejecuta solo a demanda. Antes de cada ejecución se validan contigo la ejecución y los escenarios.
  • Los flujos usan identificadores, no textos, así que funcionan igual en español e inglés.
  • Appium no tiene suite propia en el MVP. Los identificadores quedan listos para que QA la construya.
